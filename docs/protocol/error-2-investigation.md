# Real-phone investigation: Android Auto "Error 2" after `ServiceDiscoveryResponse`

## Status: open, unresolved, but the failure boundary keeps moving further into the session with each increment — and has now changed character twice. Three early hypotheses tested and refuted; advertising the full 8-service canonical set, then handling `AudioFocusRequest`, then `KeyBindingRequest` on the Input channel, then `Setup`/`Config`/`Start` on all three `AudioMediaSinkService`-derived channels (`MediaAudio`/`SystemAudio`/`SpeechAudio`), each produced real forward progress — the phone now opens every channel, drives video and all three audio channels through `Setup`→`Config`, and completes a full key-binding round trip. With `SpeechAudio` handled, the probe no longer hit an explicit "unexpected message" rejection at all: it ran every implemented handshake step successfully and then **timed out** waiting for anything further from the phone. A fourth hypothesis — that the phone just needed more time before sending whatever comes next, so the 10s `PROBE_TIMEOUT` was the limiting factor — was tested and refuted: raising it to 30s produced no behavioral difference. A fifth hypothesis — that the phone expects the head unit to proactively send `PingRequest` every 5 seconds as a session-liveness signal (matching `OpenAuto`'s `AndroidAutoEntity`/`Pinger`) — was implemented and tested, but the probe itself hit a new, reproducible local failure (a USB bulk-OUT write timeout) right around when the first ping would be sent, before the hypothesis could be fairly observed; still unresolved. A systematic diff against `OpenAuto`'s full post-`ServiceDiscoveryResponse` session lifecycle (rather than one hypothesis at a time) then surfaced a sixth, better-evidenced hypothesis — this project's `ServiceDiscoveryResponse` had never advertised any sensor capability at all (`Sensors` was encoded as an empty message), so the phone had no way to know it could request `DRIVING_STATUS`/`NIGHT_DATA`, described in the research as eager/near-mandatory session-bring-up behavior. This was implemented and tested twice more: first with `PingRequest` neutralized (clean timeout, `SensorRequest` never arrived), then — after implementing a seventh increment (`NavFocusRequest`/`ByeByeRequest`, below) — with `PingRequest` active at 5s, where a real run reached `SensorRequest`/`SensorResponse`/`SensorBatch` for the **first time ever** before hitting the write timeout again. Neutralizing `PingRequest` a second time reproduced the identical sensor exchange with a clean timeout instead, confirming the write timeout is specifically tied to the ping write rather than incidental USB flakiness. Neither `NavFocusRequest` nor `ByeByeRequest` ever arrived in either clean run, even after the full sensor exchange completed — refuted, or at minimum not yet observed. Diagnosing the ping write-timeout confound directly (at the user's request) refuted two more candidate causes — switching `PingRequest` to TLS-encrypted framing, and raising this project's bulk-OUT write timeout to match AASDK's own reference value (10s) — neither stopped the write from timing out, meaning the phone had already stopped servicing the connection by that point regardless of what was sent next. A direct, targeted comparison against a second, independent, working Android Auto implementation (`f-io/LIVI`, GPL-3.0-or-later, not AASDK-derived) at the user's request then found the actual gap: LIVI sends an unsolicited `VideoFocusNotification` granting video focus immediately after `Config`, something this project had never sent at all despite the message pair already existing in this project's own pinned AASDK schema. **Implementing this produced the first real breakthrough in this entire investigation: the phone sent `Start` on the video channel for the first time ever, and the probe reached its own internal success condition (`probe_result=video_channel_start_received`).** Error 2 still appeared on the phone screen even then — but since this probe deliberately never sends any real video/audio media data after `Start` (out of scope; see the module doc comment), the leading theory now is that Error 2 at this point reflects the complete absence of a following media stream, not a remaining wire-protocol defect — a fundamentally different, more optimistic conclusion than everything tested before it, though not yet confirmed. Error 2 has appeared on screen in every run so far regardless (confirmed on eleven separate real-phone runs total across all increments) — but the failure boundary has now moved past every wire-protocol step this probe implements. A comprehensive, whole-session LIVI audit (at the user's explicit request, replacing the narrow per-message comparisons above) then found two more concrete gaps — no `MEDIA_MESSAGE_ACK` was ever sent despite advertising `Config.max_unacked = 1` on every AV channel, and `KeyBindingResponse` was more strict than LIVI's own unconditional-`OK` behavior. Both implemented and real-hardware tested (thirteenth run): the probe now reaches `Start`, keeps observing for real media data, and completes its entire observation window with **no local error of any kind** — but `Data`/`CodecConfig` still never arrived on the video channel, and Error 2 still appeared. That run's short window (~1-2 real seconds after `Start`) left open whether it was simply too short to be conclusive. A fourteenth run directly tested that: `PROBE_TIMEOUT` raised 10s→30s, same clean-completion result, but this time with the full 30-second window elapsing — still no `Data`/`CodecConfig`, still Error 2. **This refutes the "window too short" hypothesis.** The leading theory is now that the phone simply does not intend to send media data on this session at all, regardless of how long the head unit waits — plausibly because a real head unit needs to already be behaving like a genuine media sink (decoding/rendering, or some other liveness signal) before the phone commits to streaming, not just correctly complete the wire handshake. See "30-second observation window" below. A separate, lower-layer check — swapping the AOA accessory identification strings for the exact pinned-AASDK reference values, combined with the real operator-authorized credential — was also tried (two more real-phone runs, fifteenth and sixteenth) and showed no evidence of helping; reverted. See "AOA identity experiment" below. A follow-up research pass (no code, no real-hardware trial) checked whether LIVI avoids Error 2 by tracking a fresher AA protocol: LIVI's own version-negotiation history shows it started below even AASDK's `1.6` ceiling and only reached `1.7` in June 2026, backed by real new message support, not a bare version-string claim — consistent with, and reinforcing, this project's own earlier finding that claiming `1.7` alone changes nothing. See "Does LIVI avoid Error 2 by tracking a fresher protocol?" below. A seventeenth real-phone run then tested the one concrete gap that research pass's own audit had left out — LIVI advertises a 1500ms ping cadence via `ServiceDiscoveryResponse.connection_configuration.ping_configuration`, never before populated in this project — but the run itself didn't reach video `Start` this time, so the result is **inconclusive, not refuted**, consistent with this investigation's already-documented run-to-run variability. See "Ping cadence advertisement experiment" below. LIVI was then formally adopted as a licensed source (`docs/protocol/livi-adoption.md`) and a full-codebase research pass found its actual ping *behavior* (armed immediately after `ServiceDiscoveryResponse`, 1500ms cadence, a local 5000ms watchdog) differs from the `OpenAuto`-derived model every prior ping trial used. An eighteenth real-phone run implementing this exact model got the first-ever real `PingResponse` back from the phone — but the *second* scheduled ping hit the identical write timeout as every prior trial, refuting the specific "wrong timing causes the write timeout" theory even as it narrows the bug's characterization. Still Error 2. See "LIVI formally adopted; real ping-timing trial" below. Following an external analysis's recommended order, a full message-by-message LIVI `Session.ts` timeline diff was then run: it found and this project now implements `VideoConfiguration.ui_config` (never populated before, LIVI's own default all-zero value applies directly to this project's single fixed video tier), confirmed `VideoFocusNotification`'s wire bytes already match LIVI exactly (no gap), and turned up no other well-evidenced Error-2 candidate. Per-write USB diagnostic instrumentation was also added, and the analysis confirmed this project's own write path is already fully serialized (single-threaded, no concurrent writes) — if the second-ping write timeout is a concurrency bug, it isn't in this project's own code. Both changes were then tested together on real hardware (nineteenth run): reached `Start`/`channel_setup_complete` again, `ui_config` showed no evidence of changing anything, and the instrumentation caught the second-ping write genuinely blocking for the full 10s `BULK_SEND_TIMEOUT` at the libusb level before failing — not a fast rejection — with the immediately preceding non-ping writes completing instantly. Still Error 2. See "`ui_config` implemented; USB writes instrumented" below. A twentieth run then isolated the variable directly: on the second scheduled proactive send, a harmless non-ping message (a duplicate `VideoFocusNotification`) was substituted for the second `PingRequest`. **It hit the identical failure** — same blocking `write_bulk` call, same ~10s timeout, same point in the session. This is decisive: the failure has never been about `PingRequest` specifically, it's about a *second proactive, unsolicited write* of any kind at this point in the session — refuting every ping-content/timing-specific fix attempted so far (items 7, 8, 15). Local causes (clock desync, USB power/signal) were checked and ruled out. Still Error 2. See "Ping isolation experiment" below. A real `GStreamer` decode/render pipeline was then built and wired into the probe (no longer just a capability probe) and confirmed starting cleanly against real hardware on a twenty-first run — but it was never fed a frame, since the phone still never sent `Data` before the same write-timeout bug ended the session. Still Error 2, unchanged; see "Real GStreamer decode/render pipeline" below. A twenty-second run then directly tested whether the write-timeout endpoint ever recovers, rather than just failing once: an opt-in experiment made proactive-write timeouts non-fatal (instead of ending the whole probe on the first one, as every prior trial did) and extended the observation budget to 120s. **The endpoint never recovered: the first ping succeeded normally, then 11 consecutive scheduled proactive sends in a row all failed identically over the following ~110 seconds, confirmed at the raw USB level (`usbmon`: 25 successful bulk-OUT writes, then 11 consecutive `-2`/ENOENT host-side-cancellation completions, no `STALL`, zero recoveries).** This decisively rules out "temporarily busy" as an explanation for the write timeout — once the phone's endpoint stops answering proactive writes, it stays that way, at least for as long as this project has ever observed. Still Error 2. See "Proactive-write survival experiment" below. Two more real-phone runs then tried the other half of that same question — is the failure really about a write being *proactive*, or about elapsed idle time regardless of who initiates — by gating every proactive send on immediately following a genuine reactive frame from the phone. **Both runs found the same thing, and it wasn't the answer to that question: the phone stops sending anything at all, on any channel, a few messages after `Start` — not just failing to answer proactive writes.** With no reactive traffic left to hook a gated proactive send onto, neither trial ever got to attempt a second send, so the experiment is inconclusive on its original question but reveals something new: the session's silence isn't selective to unprompted head-unit writes, it's total. Still Error 2 both times. See "Reactive-triggered proactive-send experiment" below. **Then the decisive result: running `f-io/LIVI` (already an adopted reference source) directly against this same phone, on this same Pi, produced a full, real, working Android Auto session — confirmed on both physical screens, and confirmed at the raw USB level (4,664 consecutive successful bulk-OUT writes, zero failures, versus this project's own probe's never getting past a couple).** This proves the phone/cable/USB stack were never the problem. The most concrete lead: LIVI advertised both H.264 and H.265, and the phone actively chose H.265 for both video streams — a codec this project has never advertised at all. Not yet proven as the fix, but now the best-motivated, most specific, most actionable hypothesis this investigation has produced. See "LIVI known-good capture" below. H.265 advertisement was then implemented (schema-only, same 800x480 tier as the existing H.264 config) and tested twice on real hardware: **the phone picked H.264 both times, not H.265, and both trials reproduced the exact pre-existing write-timeout failure.** This narrows the hypothesis rather than refuting it — LIVI also advertised a larger 1280×720 resolution tier, not just a second codec, which this project has never advertised at any resolution; resolution tier is now the next candidate variable. See "H.265 advertisement implemented and tested" below.

## Ping/liveness experiment (most recent, real hardware, inconclusive)

`OpenAuto`'s `AndroidAutoEntity::start()` (`AndroidAutoEntity.cpp`) arms a `Pinger` immediately at session start — before even `VersionRequest` — that proactively sends `PingRequest` every 5 seconds for the life of the session (`AndroidAutoEntityFactory.cpp`'s hard-coded `std::make_shared<Pinger>(ioService_, 5000)`), completely decoupled from handshake/channel-setup progress. This project had never implemented this at all. Given the post-`SpeechAudio` symptom is "the phone goes quiet," a plausible theory is that a real phone treats ping receipt as its own liveness signal, independent of whatever else is happening in the session — which would explain both the timeout and the previously-observed run-to-run variability.

Implemented: `write_int64_field` (`protobuf.rs`, needed since epoch-millisecond timestamps exceed `i32::MAX`), `ControlMessageId::PingRequest`/`PingResponse` (wire values 11/12, confirmed via `ControlMessageType.proto`), a new `crates/protocol-aap/src/ping.rs` (`encode_ping_request`/`decode_ping_response`, matching `OpenAuto`'s own scope exactly — it never sends `PingResponse` or decodes an incoming `PingRequest`), and `PING_INTERVAL`/`send_ping_request`/a `PingResponse` arm in `auth_discovery_probe.rs`. Confirmed directly from the pinned AASDK source (`ControlServiceChannel.cpp`): both ping messages are sent `EncryptionType::PLAIN`, `MessageType::SPECIFIC` — unencrypted, unlike virtually everything else post-handshake — so `send_ping_request` uses the same plain-frame `send_control` helper already used for `VersionRequest`/`EncapsulatedTls`/`AuthComplete`.

Two consecutive real-phone runs (fresh MTP replug before each) both produced the same new, reproducible result — not the previous clean `auth/service-discovery/channel-setup probe timed out before completion`, but a local I/O failure:

```
...(video/MediaAudio/SystemAudio/SpeechAudio all opened, AudioFocusRequest handled, all four channels' Setup/Config exchanged, key binding answered)...
probe_state=speech_audio_channel_setup_config_sent   # Run 1's last successful line
error=transport I/O: USB error: USB transfer timed out
```

```
...(same shape, different config-send ordering)...
probe_state=video_channel_setup_config_sent           # Run 2's last successful line
error=transport I/O: USB error: USB transfer timed out
```

In both runs, the failure landed immediately after the last of the four `Setup`/`Config` exchanges completed — i.e., right around the ~5-second mark, exactly when `PING_INTERVAL` first fires. This is a **new class of failure**: a `TransportError` surfacing from `LibUsbBulkTransport::write_all`'s bulk-OUT write (`CONTROL_TIMEOUT`-style 2-second timeout in `write_all`, `transport-usb/src/linux.rs`), not a clean protocol-level timeout — never observed in any prior run, across four earlier increments, before ping code was added. **Confirmed on the phone screen for both runs: still Error 2.**

This result is **inconclusive for the ping hypothesis itself**: the probe crashes locally before it can be observed whether continued pinging would have changed the phone's behavior. It's not yet established whether the ping write is the literal cause of the USB stall (as opposed to the *next* write after it, or ordinary real-hardware USB flakiness that happens to coincide with this point in the deterministic handshake timeline) — that needs its own targeted investigation before this hypothesis can be fairly tested. The code is left in place (not reverted) since it's a reasonable, `OpenAuto`-matched implementation regardless of the outcome, and the write-timeout finding is itself useful information for whoever picks this up next.

## Systematic `OpenAuto` diff and the Sensors capability-advertisement experiment (most recent, real hardware, refuted)

The strongest finding: `service_discovery_response.rs`'s `ServiceKind::Sensors` arm was encoding `Service.sensor_source_service` as an **empty message**, never populating `SensorSourceService.sensors` (the repeated list of supported `SensorType`s). ## Ping write-timeout diagnosis (real hardware, both attempts refuted)

At the user's explicit request, the ping write-timeout was diagnosed directly rather than continuing to work around it. A bracketing diagnostic print (`probe_state=ping_request_send_attempt`, immediately before the send call) was added first, to remove any doubt about which write was stalling.

**Attempt 1: switch `PingRequest` from plain to TLS-encrypted framing.** This project's `send_ping_request` had always sent `PingRequest` unencrypted, matching AASDK's own `sendPingRequest` (`EncryptionType::PLAIN`) — the only post-handshake message this probe ever sent that way. Theory: a real `1.7`-speaking client might expect an unbroken all-encrypted bytestream and desync on a stray plain frame badly enough to stop draining its own USB OUT buffer. Tested with `PingRequest` active as normal: the write **still** timed out, and `probe_state=ping_request_send_attempt` was again the last printed line — confirming definitively (not just by timing correlation) that it's the ping write itself that stalls, but refuting the encryption-domain theory. **Confirmed on the phone screen: still Error 2.**

**Attempt 2: raise the bulk-OUT write timeout to match AASDK's own reference value.** Deep research into `OpenAuto`/AASDK's actual send-path mechanics (`Pinger.cpp`, `AndroidAutoEntity::sendPing`/`schedulePing`, and the full `ServiceChannel`→`Messenger`→`Transport`→`USBTransport`→`USBEndpoint` send chain) found the ping is not prioritized, delayed, or specially scheduled anywhere in that reference implementation — it enters the exact same generic FIFO send queue as every other control message. But it also found `include/f1x/aasdk/Transport/USBTransport.hpp`'s `cSendTimeoutMs = 10000` — a **10-second** per-transfer libusb write timeout, used for literally every bulk-OUT transfer, versus this project's own **2-second** timeout for the same operation (`crates/transport-usb/src/linux.rs`). Raised to match (`BULK_SEND_TIMEOUT = 10s`) and tested with `PingRequest` active: the write **still** timed out (again confirmed via the bracketing print, still the last line). Since even 5x more time didn't help, this rules out "the phone was just briefly slow" — the write genuinely never completes at all. **Confirmed on the phone screen: still Error 2.**

A separate research pass into `f-io/LIVI` (a second, independent, GPL-3.0-or-later Android Auto implementation, not AASDK-derived, done at the user's request specifically to look at how a real working implementation handles this) found its own bulk-OUT writes are serialized through a single promise chain (`UsbAoapBridge.ts`'s `_outChain`) so no two writes are ever issued concurrently — but this doesn't apply to this project's own architecture, since `run()`'s loop is already single-threaded and fully synchronous (every `send_all()` call already blocks to completion before the next is issued). No adoptable fix came from this angle.

Both refutations, taken together with what came next (see below), now support a different reading: the write never completing regardless of content or timeout length is consistent with the **phone having already stopped servicing the USB connection by that point**, independent of what this probe tries to send next — not a bug in how the ping is sent at all.

## Comprehensive LIVI audit, `MEDIA_MESSAGE_ACK`, and `KeyBindingResponse` (real hardware — clean run, still no `Data`)

At the user's explicit direction — after repeated real-hardware runs kept finding one gap at a time — this pass replaced narrow, single-message comparisons with one comprehensive audit of `f-io/LIVI`'s **entire** session lifecycle: every channel, every message, from connection through active streaming (not just the video Setup/Config/Start sequence the earlier `VideoFocusNotification` comparison targeted). ## AOA identity experiment (real hardware, two trials — inconclusive, reverted)

While researching whether the AOA (Android Open Accessory) transport layer itself — a level below the AAP wire protocol entirely, governing USB accessory-mode transition before `VersionRequest` is ever sent — could explain Error 2, one genuinely untested variable was found: the six accessory identification strings (manufacturer/model/description/version/uri/serial). `usb auth-discovery-probe` has always used `AoaIdentification::receiver_probe()` (this project's own `uri`/`serial`); a second preset, `aasdk_compatibility_probe()`, using the exact pinned-AASDK reference `uri`/`serial` values, already existed in the codebase but had only ever been tried once, paired with a now-permanently-disabled temporary generated TLS credential — that combination was rejected with Android Auto error 7 (a TLS-trust rejection, unrelated to these strings). It had never been tried with the real, operator-authorized credential this project now uses.

Stated honestly going in: low confidence. Error 2 fires deep into the session (after service discovery, all channels open, video `Start`) — well past where AOA-level identity would plausibly matter, since that governs whether the phone launches Android Auto at all, which it already reliably does. Run as a cheap elimination, not a leading theory.

`usb_auth_discovery_probe` (`main.rs`) was switched to `AoaIdentification::aasdk_compatibility_probe()`; `PING_INTERVAL` stayed neutralized (`3600s`) to avoid the still-unresolved ping write-timeout confounding this specific variable. Two real-hardware trials, both after a fresh replug:

- **Trial 1 (fifteenth real-phone run):** stalled after the sensor exchange (`SensorRequest`/`DrivingStatusData` handled), before video `Config` was even sent. Timed out. **Confirmed on the phone screen: Error 2.**
- **Trial 2 (sixteenth real-phone run):** got further — video `Config`/`VideoFocusNotification` sent, all three audio channels' `Config` sent, two sensor exchanges (`DrivingStatusData`, `NightMode`) — but still never reached video `Start`, and timed out. **Confirmed on the phone screen: Error 2.**

Neither trial reached `Start`, which the two most recent `receiver_probe()` trials (thirteenth and fourteenth runs) both had. This is suggestive but not strong evidence of a regression: this investigation has already documented substantial run-to-run variability with *identical* code (see "What this rules out, and what it doesn't" below), so two non-`Start` runs in a row is within the range already observed before this variable was ever touched. What the two trials do establish cleanly: this identity swap shows **no evidence of helping**, and Error 2 appeared both times regardless of how far the session got. `usb_auth_discovery_probe` has been reverted to `AoaIdentification::receiver_probe()`; `aasdk_compatibility_probe()` remains in the code only as a record of what was tried (see its doc comment, `crates/transport-api/src/lib.rs`).

## Does LIVI avoid Error 2 by tracking a fresher protocol? (research, no code change)

At the user's explicit request — to resolve Error 2 before doing anything else, and to check whether LIVI's success comes from being a current, actively maintained implementation that tracks Google's latest AA protocol, versus an older hack, and whether the operative factor is protocol freshness, capability/version matching, or simply avoiding unmaintained libraries — this was checked directly against `f-io/LIVI`'s own GitHub history (commit dates, diffs, issues), not just its current code. No LIVI code is reproduced below, only cited facts (dates, commit messages, version numbers).

**LIVI is genuinely very actively maintained.** Created 2025-05-02, `pushed_at` 2026-08-13 (the day before this check), commits nearly every day, a formal release cut 2026-07-30 (`8.1.0`). That much supports "actively maintained."

**The more specific and more decisive finding is in LIVI's own version-negotiation history.** `VERSION.MAJOR`/`MINOR` (`stack/constants.ts`) started at **`1.1`** in LIVI's very first commit (2025-05-01, `feat(android-auto-native): initial Linux implementation`) — *lower* than even the AASDK forks this project is based on (pinned at `1.6`). It only reached **`1.7`** on 2026-06-04, over a year later, in a commit titled `feat(aa-nav): destination distance + ETA via the modern (1.7) nav path` (SHA `9499aaa4`). That commit is not a cosmetic version-string bump — it adds real capability alongside it: `NavigationStateUpdate`/`NavigationPositionUpdate` message handling in `NavigationChannel.ts`, with the diff itself commented `Modern nav (AA ≥ 1.7): current step maneuver/road + destination address` throughout. LIVI claimed `1.7` only once it had implemented the message shapes that tier implies, wire-encoded as a single fixed `major.minor` pair in `VERSION_REQUEST` (`Session.ts`'s `_sendVersionRequest`) — the same shape AASDK and this project both use, not a negotiated range.

**This points to capability/version matching as the operative mechanism, not protocol freshness or "maintained vs. abandoned" as such** — three points converge on that reading:

1. Claiming a version number is cheap; LIVI backed theirs with real message support before claiming it, and the version-request wire shape (a single fixed pair, not a range) means the phone has no way to tell the difference between an honest claim and a bare one from the handshake alone.
2. This project already tested the cheap version, independently, earlier in this investigation: offering `1.7` instead of the pinned `1.6` with nothing else changed produced **no difference** (see "Hypotheses tested against real hardware and refuted", item 2, below). That's direct confirmation from our own side that the version number alone isn't the gate.
3. AASDK itself is not actually abandoned — the pinned fork's `newdev` branch was pushed as recently as 2026-06-11 — it has simply never reverse-engineered the `1.7`-tier message set. So "unmaintained library triggers a fingerprint check" isn't quite the right frame either; it's "hasn't reached capability parity with what current phones expect," independent of how active the repository is.

**Honesty caveat:** no LIVI commit or issue found frames any of this as "fixing Error 2" — the `1.7` bump is presented purely as a nav feature addition, and a search of that repository's issues turned up no report of an "incompatible software" rejection at all. This is inference from primary-source evidence (dated commits and diffs), not a documented claim by LIVI's own author.

**What this means for this investigation:** the one concrete overlap — navigation — is something already separately ruled out here (`NavFocusRequest`/`ByeByeRequest` have never arrived in any real run; see item 6 in "Hypotheses tested against real hardware and refuted"), so LIVI's specific `1.7` addition is not itself the blocker for this project. This research doesn't hand over a new fix. It reinforces the already-leading theory by elimination: with version-badge-matching now shown (by LIVI's own evidence, not just this project's) not to be what separates a working client from a rejected one, and every other tested handshake-level explanation already refuted (see "What this rules out, and what it doesn't" below), the complete absence of a real media stream after `Start` remains the best-supported explanation for Error 2.

## LIVI formally adopted; real ping-timing trial (real hardware — first-ever real `PingResponse`, but write timeout still recurred)

At the user's explicit direction, `f-io/LIVI` was cloned in full (into the session scratchpad, never into this repository) and formally adopted as a GPL-3.0-or-later source under the same gate OpenAuto/AASDK went through — pinned revision `9000f308eec423c5c56ac0a14491a7c95ce5762d`, file-level provenance, and defined scope/exclusions recorded in `docs/protocol/livi-adoption.md`. `THIRD_PARTY_NOTICES.md` and `docs/architecture/decisions/0002-android-auto-protocol-source-gate.md` were updated to match. LIVI's own credential material (`native/crypto/**`) was explicitly excluded and never read for content; this project continues to use only its own operator-authorized credentials from `/etc/aa-headunit/credentials`.

A full-codebase research pass (not just the targeted file lookups every prior LIVI comparison used) found LIVI's actual ping *behavior* differs from the `OpenAuto`-derived model this project's every prior ping trial was based on, in two ways at once:

- **Arm timing:** LIVI arms its ping timer immediately after sending `ServiceDiscoveryResponse` — before any channel is even opened — not before `VersionRequest` (`OpenAuto`'s `AndroidAutoEntity::start()` timing, which every prior trial in this investigation used).
- **Cadence:** 1500ms, not `OpenAuto`'s 5000ms.
- **A local watchdog** with no `OpenAuto`/`Pinger` equivalent: LIVI closes its own session if no `PingResponse` arrives within 5000ms of the last one.

No real ping had ever reached the phone at this exact timing before — every prior ping trial used the `OpenAuto`-derived model, which was neutralized (`PING_INTERVAL = 3600s`) for most of this investigation specifically because of the still-unresolved USB bulk-OUT write timeout. The working theory going into this trial was that the write timeout might itself be a symptom of the wrong ping timing, not an independent confound.

Implemented in `apps/aa-headunit-diagnostics/src/auth_discovery_probe.rs`: `PingState` (armed only once `ServiceDiscoveryResponse` is sent, via `handle_message`), `PING_INTERVAL` changed from the neutralized `3600s` to the real `1500ms`, and a new `PING_WATCHDOG_TIMEOUT = 5s`. `PingConfiguration` (`crates/protocol-aap/src/service_discovery_response.rs`) was also completed with all four sub-fields (`timeout_ms=5000`, `interval_ms=1500`, `high_latency_threshold_ms=500`, `tracked_ping_count=5`), all now backed by the adopted source rather than left unmodeled.

That's a narrower, more specific characterization of the bug than before, even though its root cause remains unresolved.

Two new unit tests with hand-verified exact bytes. Formally recorded in `docs/protocol/livi-adoption.md` ("Adopted scope" item 6).

**2. USB bulk-OUT write instrumentation.** Per-write diagnostic logging added to `crates/transport-usb/src/linux.rs` (`LibUsbBulkTransport::write_all`/`read`): a monotonically increasing per-transport `write_id`, byte length, the frame's leading byte (`channel_id`, since that's the first on-wire byte of every AAP frame), start/elapsed timing for both the overall write and each individual `write_bulk` chunk, and explicit success/timeout/error outcomes — printed as `usb_write_start`/`usb_write_chunk`/`usb_write_complete`/`usb_write_error`/`usb_read_complete`/`usb_read_error` lines alongside the probe's existing `probe_state=...` output. This gives the next real-hardware trial precise, byte-level visibility into the still-unresolved second-ping write timeout that no prior trial had.

Also confirmed and documented directly in code: this crate has exactly one `SessionTransport` consumer (`aa-headunit-diagnostics`), and `write_all`/`read` are only ever called from that single-threaded probe's own receive loop — one bulk transfer at a time, never concurrently. There is no overlapping-write bug in this project's own Rust code (verified: no `thread::spawn`/async anywhere in `auth_discovery_probe.rs` or `protocol-aap`). If writes are genuinely overlapping or blocked, the cause is below this layer (kernel USB stack, libusb's own internal state, or the phone's own USB peer) — a **serialized outbound queue is already the architecture today**, not a fix that still needs building. This directly answers one part of the recommended next step ("treat the second outbound ping timeout as a transport/concurrency bug until proven otherwise") — concurrency in this project's own code is ruled out; the two controlled real-hardware variants suggested (send a harmless non-ping frame at the second-ping point; suppress all other traffic and send only pings) remain available as a genuinely separate follow-up experiment if the instrumented data from the next trial doesn't resolve it on its own.

**3. Video-focus wire bytes — checked, already correct, no change needed.** The research pass confirmed LIVI sends `VideoFocusIndication`'s payload as exactly `0x08 0x01` (field 1, varint, value 1 = PROJECTED). This project's own `encode_video_focus_notification(VideoFocusMode::Projected)` (`video_setup.rs`) already produces byte-identical output (`VideoFocusMode::Projected.wire_value() == 1`, field 1, int32). Confirmed match, not a gap.

**Other findings, lower priority, not yet implemented:** LIVI also populates three more still-unmapped `ServiceDiscoveryResponse` top-level fields this project doesn't — `driver_position` (LIVI sends the default `0`/`DRIVER_POSITION_LEFT`), `display_name` (LIVI sends the literal string `'LIVI'`), and `probe_for_support` (LIVI hardcodes `false`). None came with any signal suggesting they're load-bearing for Error 2; cheap, well-attributed additions if pursued later, not prioritized this pass. `session_configuration` is unset by LIVI too (not a gap). `canPlayNativeMediaDuringVr` — a field this project's own docs already correctly flag `[deprecated = true]` upstream and deliberately exclude — is set `true` by LIVI despite that; noted as a real divergence but VR-specific and not recommended as an Error-2 candidate. LIVI's audio-focus `RELEASE`-mapping (a class of bug LIVI's own code comments describe as previously causing the phone to silently close the session) was cross-checked against this project's `grant_audio_focus`: already mapped correctly (`Release → Loss`), not a gap.

Verification (fmt/check/clippy/test/secret-scan/`.deb` rebuild+install) is clean.

**Real-hardware result (nineteenth run), both changes together:** this run reached video `Start` and `channel_setup_complete` again (`ui_config` didn't break anything already working), then a second `SensorRequest`/`SensorResponse`/`SensorBatch` round trip (`NightMode`) completed normally — both of those writes returned in 0-1ms, instantly. The scheduled second `PingRequest` then hit the identical failure every prior ping trial has hit, but the instrumentation now shows *how* it fails: `write_bulk` itself blocked for the entire 10-second `BULK_SEND_TIMEOUT` before libusb returned `Operation timed out` — not a fast rejection, a genuine hang at the USB transfer layer, with nothing else in flight at the time (the immediately preceding sensor-response/batch writes had already completed and returned before the ping write began). **Confirmed on the phone screen: Error 2.**

This is the first time this investigation has direct evidence of *how* the second-ping write fails, not just *that* it fails: the OUT endpoint itself stops accepting data at that point, for however long `BULK_SEND_TIMEOUT` allows waiting. Combined with the immediately-prior non-ping writes succeeding instantly, this is consistent with — though not yet proof of — the phone (or something between the phone and this project's USB stack) specifically declining to service a second unsolicited `PingRequest`, rather than a generic "too many writes" or concurrency issue. `ui_config` itself shows no evidence of changing anything (still Error 2, same failure point as the immediately preceding ping-timing trial).

The prior three hypotheses (below) each produced **zero change** in behavior — the phone rejected `ServiceDiscoveryResponse` identically every time, which was itself a strong hint that the problem was structural rather than a single missing field. Externally-sourced research (AASDK/OpenAuto/LIVI all construct a complete, fixed 8-service `ServiceDiscoveryResponse` unconditionally, not a curated subset) was checked directly against this project's already-approved `OpenAuto` primary source (`ServiceFactory.cpp`) and confirmed: `ServiceFactory::create()` unconditionally constructs 7 of 8 canonical services, with the 8th config-gated but on by default.

Implementing the full canonical set (`Video`, `Input`, `MediaAudio`, `SystemAudio`, `SpeechAudio`, `Sensors`, `Bluetooth`, `Microphone` — `crates/protocol-aap/src/service_discovery_response.rs`, generic `ChannelOpenStateMachine` reused per channel in `auth_discovery_probe.rs`) was the first change in this entire investigation that altered real-phone behavior: the phone stopped rejecting `ServiceDiscoveryResponse` and instead proceeded into the session, first sending a previously-unseen encrypted control message (`AudioFocusRequest`, control ID 18). Implementing and answering that (`crates/protocol-aap/src/audio_focus.rs`, `AudioFocusNotification` granting exactly what's asked — see that file's doc comments for full wire provenance against the pinned AASDK source) unblocked the phone further still: it proceeded to open all 8 channels and drive the video channel through `Setup`→`Config`, then send `KeyBindingRequest` on the Input channel.

Implementing and answering that too (`crates/protocol-aap/src/input_message.rs`, `KeyBindingRequest`/`KeyBindingResponse` — see that file's doc comments for full wire provenance; policy in `handle_input_channel_message`/`evaluate_key_binding_request` in `auth_discovery_probe.rs`, mirroring `OpenAuto`'s `InputService::onBindingRequest` validation against the head unit's own advertised keycode list) unblocked the phone yet again: the empty request was answered `Success` and accepted, and the session proceeded to a new message — `Setup` — on the `MediaAudio` channel.

Implementing that too (`crates/protocol-aap/src/audio_setup.rs`, a deliberate duplicate of `video_setup.rs` rather than a shared generic state machine, to avoid touching the real-hardware-proven video code path — see that file's doc comments for full wire provenance) unblocked the phone yet again: the `Setup` (requesting `MEDIA_CODEC_AUDIO_PCM`) was answered with `Config` and accepted, and the session proceeded to a new message on the `SystemAudio` channel.

`SystemAudio` also turned out to be a thin `AudioMediaSinkService` subclass in AASDK, advertising the same single-PCM-configuration shape this project already advertises for it — so no new crate-level code was needed at all; `AudioSetupStateMachine` was reused unmodified, with only a parallel `SystemAudioChannel` enum/`handle_system_audio_channel_message` dispatch added in `auth_discovery_probe.rs` (mirroring the `MediaAudio` wiring exactly, purely additive — the just-proven `MediaAudio` code was never touched). This unblocked the phone yet again: `SystemAudio`'s `Setup` was answered with `Config` and accepted, and the session proceeded to a new message on the `SpeechAudio` channel.

`SpeechAudio` (AASDK's `GuidanceAudioChannel`, matching `AudioStreamType::Guidance`) turned out to be the third and final thin `AudioMediaSinkService` subclass, advertising the same single-PCM-configuration shape again — so once more, no new crate-level code was needed; `AudioSetupStateMachine` was reused unmodified for a third channel, with only a third parallel `SpeechAudioChannel` enum/`handle_speech_audio_channel_message` dispatch added, purely additive. This is where the pattern changed: with all three audio channels' `Setup`/`Config`/`Start` handling in place, the probe no longer hits an explicit "unexpected message" rejection at all on a subsequent real-phone run — it runs every implemented handshake step to completion and then times out. Error 2 still appears on screen regardless (confirmed on two separate runs), but the failure signature is now "the phone goes quiet" rather than "the phone sends something new we reject."

## Ping isolation experiment (real hardware — decisive: refutes "ping-specific", confirms "second proactive write, any content")

At the user's direction, following an external analysis's suggested isolation technique: on the *second* scheduled proactive send only (the first stays a real `PingRequest`, already proven to succeed), substitute a harmless, already-proven-safe unsolicited message — a duplicate `VideoFocusNotification(Projected)` on the video channel, the same message this probe already sends exactly once, unconditionally, right after video `Config` — instead of a second `PingRequest`. Gated behind an opt-in `AA_HEADUNIT_PING_ISOLATION` environment variable (`apps/aa-headunit-diagnostics/src/auth_discovery_probe.rs`'s `PingState.sends_since_arm`, `service_ping`, `send_control_probe_frame`); off by default, no effect on normal runs.

Real-hardware result, one trial after a fresh replug:

```
...(version negotiated 1.7, TLS complete, service discovery summary received, response sent, first PingRequest sent and PingResponse received, all 8 channels opened, key binding, video Config/VideoFocusNotification sent, all three audio channels' Config sent, two sensor exchanges, video Start received, channel_setup_complete)...
probe_state=speech_audio_channel_setup_config_sent
probe_state=ping_isolation_control_frame_send_attempt
usb_write_start write_id=26 bytes=37 channel_id=Some(1) timeout_ms=10000
usb_write_error write_id=26 offset=0 elapsed_ms=10000 error=Operation timed out
error=transport I/O: USB error: USB transfer timed out
```

**The substituted control frame — not a `PingRequest` at all, sent on the video channel instead of the control channel — hit the identical failure: `write_bulk` blocked for the full 10-second timeout before failing, at effectively the same point in the session every prior trial has failed at.** Confirmed on the phone screen: Error 2.

**This is decisive, not just suggestive.** It directly refutes the hypothesis motivating every ping-specific fix attempted in this investigation (items 7, 8, 15) — the failure has never been about `PingRequest`'s content, encryption, or timing. It's specifically about attempting a **second proactive, timer-fired, unsolicited write** at this point in the session, regardless of what that write contains or which channel it's on. Everything reactive (responses to phone-initiated messages — channel opens, `Setup`/`Config` exchanges, sensor requests, key binding) continues to succeed instantly and indefinitely throughout the session; only the second-and-later *unprompted* write ever fails.

Two follow-up checks, both to rule out mundane local explanations before treating this as protocol-level: system clock (`timedatectl status`) is NTP-synchronized with the correct date — rules out a stale/reset clock breaking something time-dependent. `vcgencmd get_throttled` reports `0x0` (never throttled/undervolted) — rules out a power-supply/USB-signal explanation, which is also inconsistent with how deterministic and reproducible the failure point is across many trials.

## `usbmon` capture (real hardware — rules out a USB STALL/explicit device rejection; the write is host-side-cancelled, never device-answered)

At the user's direction, following a further external analysis proposing that the write timeout is a transport/scheduling stall (the phone's own USB stack not actively servicing the accessory bulk-OUT endpoint for unprompted traffic) rather than anything protocol/framing-level, a raw USB-level capture was taken with the kernel's built-in `usbmon` facility — `sudo modprobe usbmon`, then reading the text-format trace directly from `/sys/kernel/debug/usb/usbmon/<bus>t` (no `tcpdump`/Wireshark install needed; debugfs was already mounted). Captured for the full duration of a normal `usb auth-discovery-probe --allow-live-aap` run (`AA_HEADUNIT_PING_ISOLATION` off, so a real third `PingRequest` is what ultimately fails this time — see below on why "third" and not "second").

Every successful bulk-OUT transfer in the trace — all ~28 of them, reactive and proactive alike, including the *first two* `PingRequest`s — shows an `S` (submit) event immediately followed by a `C` (complete) event with status `0`, typically within tens to a few hundred microseconds:

```
S Bo:025:01 -115 42 = 000b0026 17030300 219ec8ce 9638a461 76961d60 94d9cf69 d0bd4ff2 ed42826b
C Bo:025:01 0 42 >
```

The failing write looks identical at submission — same form, same size class, nothing malformed — but never gets a `C` with status `0`. It sits pending until this project's own `BULK_SEND_TIMEOUT` (10s) expires and libusb cancels it, which shows up in `usbmon` as:

```
S Bo:025:01 -115 42 = 000b0026 17030300 219ec8ce 9638a461 772e5b3c 5b6b5c61 fe70015d 7b14d0e4
C Bo:025:01 -2 0
```

`-2` (`ENOENT`) is the exact same completion status this project's own routine 500ms bulk-IN read timeouts show throughout the trace when nothing new has arrived — i.e., it's the signature of **our own side giving up and unlinking the URB**, not a status the phone's USB stack reported. Critically, **no transfer in the entire trace ever completes with a `STALL`/`EPIPE`-class status** (which would appear as a distinct nonzero code, not `-2`) — the phone's endpoint never explicitly rejects anything. The submitted write just goes unacknowledged at the host-controller level for the full window we wait.

This is genuine USB-protocol-level evidence, not just an inference from `write_bulk` blocking in our own Rust code: **the failure is not a device-side protocol rejection.** It's fully consistent with the phone's own Android Auto process not having an active read queued on that endpoint for unprompted/head-unit-initiated data at that point — the same mechanism a further external analysis proposed — though `usbmon` at this level can't fully distinguish "phone is persistently NAK-ing" from other host-side starvation; it only rules out an explicit STALL.

**Also new: in this trial, the *third* proactive send failed, not the second** (the second, like the first, completed in 26 microseconds — timestamps confirm both fired almost exactly `PING_INTERVAL` apart, matching this project's own scheduling code exactly). This run also never reached video `Start` before failing, unlike the two immediately preceding trials. Consistent with this investigation's already-extensively-documented run-to-run variability in exactly how much reactive traffic happens before the proactive-write failure — the *count* isn't fixed, but the *qualitative mechanism* (host-side timeout/cancellation, never a device-reported error) is now confirmed consistent across trials.

## Real GStreamer decode/render pipeline (real hardware — pipeline starts cleanly, never fed data, Error 2 unchanged)

Following up on the leading theory that Error 2 reflects the phone never seeing a genuine media sink (this probe has only ever byte-counted `Data`/`CodecConfig` and discarded the bytes), a real `appsrc ! h264parse ! avdec_h264 ! videoconvert ! waylandsink` `GStreamer` pipeline was implemented (`crates/media-gstreamer/src/render.rs`) and wired into `auth_discovery_probe.rs`, built lazily once `Start` is received. Proven first with a self-generated synthetic H.264 fixture (never phone-derived — no real captured content exists to test against, since the phone has never once sent `Data`).

First real-hardware run used the still-installed, pre-existing `/usr/bin/aa-headunit-diagnostics` package binary, which predated this change entirely (dated 3 August, confirmed via `strings | grep video_render` finding nothing) — that run reproduced the already-known Error 2 / write-timeout behavior with old code, not a test of the new pipeline. Re-run directly against `target/release/aa-headunit-diagnostics` (the freshly built binary containing the change): reached `Start` after the usual full handshake (all channels open, all three audio `Setup`/`Config`, both sensor exchanges), and this time **`probe_state=video_render_pipeline_started` printed with no error** — the pipeline was constructed and reached `Playing` against the real Wayland compositor already running on this Pi. This required invoking the probe as `sudo -E` rather than plain `sudo`, so `WAYLAND_DISPLAY`/`XDG_RUNTIME_DIR` survive privilege escalation; a plain `sudo` would very likely have failed to reach the compositor (logged as a recoverable `video_render_pipeline_start_failed`, not a crash, per the design) — not yet confirmed since every trial so far has used `-E`.

The pipeline was never actually fed anything: the phone still never sent `Data`/`CodecConfig`, and the session ended the same way every recent trial has — the next proactive write (`PingRequest`) hit the same unresolved 10s host-side write timeout (see "`usbmon` capture" above), then the probe exited on that I/O error. **Confirmed on the phone screen: Error 2**, unchanged. This doesn't move Error 2 forward, but it does close out a real gap in the code: the decode/render path is no longer purely theoretical/synthetic-only — it's proven to construct and start against this project's actual real-hardware Wayland session, so if a future trial ever gets a real `Data` message past the write-timeout bug, the render path is ready to actually exercise, not just log.

Two replug cycles were needed before this run: an initial attempt against a device still sitting in stale AOA-accessory mode from a prior failed session unplugged immediately, and a second attempt right after a fresh MTP re-enumeration also unplugged immediately (physical cable-seating suspected, not investigated further) — the third attempt, after the user physically reseated the cable, ran cleanly through to `Start`.

## Proactive-write survival experiment (real hardware — decisive: the endpoint never recovers, at least within 110s)

Directly follows up on suggested next step 2 from the prior session: *why* does the phone's endpoint stop answering proactive writes but keep answering reactive ones indefinitely? One candidate angle named there — a longer `usbmon` capture spanning multiple proactive-write attempts, to see whether the endpoint ever "recovers" and answers a later attempt, distinguishing "permanently stops" from "temporarily busy." Every prior real-hardware trial in this investigation ended the entire probe process on the very first proactive-write timeout (`service_ping`'s `?` propagates the `TransportError` straight out of `run()`), so no trial had ever been able to observe what happens after that point — the session always ended there.

Implemented an opt-in, off-by-default experiment (`AA_HEADUNIT_SURVIVE_PROACTIVE_WRITE_TIMEOUT`, `apps/aa-headunit-diagnostics/src/auth_discovery_probe.rs`): when set, `service_ping` logs a failed proactive write (`probe_state=proactive_write_timed_out attempt=N`) instead of returning it as fatal, and the LIVI-derived local watchdog (`PING_WATCHDOG_TIMEOUT`) is suppressed — enforcing it here would close the session the moment the first attempt went unanswered, defeating the point of the experiment. `run()` also switches to a longer observation budget (`PROACTIVE_WRITE_SURVIVAL_TIMEOUT = 120s`, versus the normal `PROBE_TIMEOUT = 30s`) so there's room for several `PING_INTERVAL`-spaced attempts. Off by default; normal probe runs (including the ping-isolation experiment) are unaffected.

Real-hardware result, one trial, `usbmon` capturing the full run in parallel:

```
...(full handshake through video Start, channel_setup_complete, real GStreamer render pipeline started — all identical to the twenty-first run)...
probe_state=ping_request_send_attempt
probe_state=ping_request_sent
probe_state=ping_armed
probe_state=ping_response_received     # first ping: succeeds normally, as in every prior trial
...(AudioFocusRequest, all channels open, key binding, video/audio Setup-Config, VideoFocusNotification, two sensor exchanges, video Start, channel_setup_complete, video_render_pipeline_started — all as in the twenty-first run)...
probe_state=ping_request_send_attempt
usb_write_error write_id=26 offset=0 elapsed_ms=10000 error=Operation timed out
probe_state=proactive_write_timed_out attempt=2 error=transport I/O: USB error: USB transfer timed out
probe_state=ping_request_send_attempt
usb_write_error write_id=27 ... elapsed_ms=10000
probe_state=proactive_write_timed_out attempt=3 ...
...(identical failure repeats for attempts 4, 5, 6, 7, 8, 9, 10, 11, 12 — write_ids 28 through 36, each blocking the full 10s BULK_SEND_TIMEOUT before failing)...
probe_result=observation_window_complete
```

Exit code 0 — the probe ran cleanly to the end of its extended 120s window, no local crash. **11 consecutive scheduled proactive sends (attempts 2 through 12) all failed identically, roughly 10 seconds apart (each attempt's own blocking write consumed almost exactly one `PING_INTERVAL`-plus-`BULK_SEND_TIMEOUT` cycle), spanning the entire remaining ~110 seconds of the window. Not one of them succeeded.**

The parallel `usbmon` capture confirms this at the raw USB level, independent of this project's own instrumentation: 25 successful bulk-OUT writes (`C Bo:1:004:1 0`, matching every reactive send plus the first ping), then 11 consecutive `C Bo:1:004:1 -2` completions — the identical host-side-cancellation signature (`ENOENT`, our own side unlinking the URB after `BULK_SEND_TIMEOUT`) found in the original `usbmon capture` section above. No `STALL`/`EPIPE`-class status anywhere in the trace. Confirmed on the phone screen: still Error 2.

**This is decisive for the specific "temporarily busy vs. permanently stopped" question, within the window actually observed:** the endpoint does not recover on its own once it stops answering proactive writes, at least not within ~110 seconds of continued, correctly-scheduled attempts. This rules out a transient scheduling hiccup or a momentary busy state as the explanation. It's consistent with — though still doesn't directly prove — the phone's own Android Auto process having durably stopped servicing that endpoint for unprompted data for the rest of the session, once whatever internal decision produces this state is made. It does not establish *why* that decision happens, and it doesn't rule out recovery over a much longer timescale than 110 seconds (not tested here). Kept in the code as a permanent, off-by-default diagnostic tool — useful for any future experiment that wants the session to survive past this point rather than dying on it.

## Reactive-triggered proactive-send experiment (real hardware, two trials — inconclusive on its own question, but reveals total post-setup silence)

Direct follow-up to the other half of suggested next step 2: is the write-timeout failure really about a write being *proactive* (head-unit-initiated, not prompted by anything the phone just sent), or is it actually about elapsed idle time on the endpoint, regardless of who initiates? Every proactive send in every prior trial fired on a bare periodic schedule — `service_ping` runs on essentially every ~500ms loop tick, since `LibUsbBulkTransport::read`'s `rusb::Error::Timeout` maps to `Ok(0)` rather than an error, so the `receive()` timeout branch in `run()`'s loop is effectively dead for the real USB transport. No prior trial had ever deliberately coupled a proactive send to genuine phone-initiated activity.

Implemented an opt-in experiment (`AA_HEADUNIT_REACTIVE_TRIGGERED_PROACTIVE_SEND`, `auth_discovery_probe.rs`): `run()`'s loop was restructured so `service_ping` is called *after* `drain_and_dispatch_frames` rather than before it, and a due proactive send is now held back until the same loop iteration where a real message from the phone was just decoded and dispatched (`drain_and_dispatch_frames`'s new `processed_any` return value) — not just a nonzero byte count, and not the routine idle polling tick. Implies the proactive-write-survival experiment's resilience behavior automatically, since this is only informative if the session survives long enough to compare attempts.

Two real-hardware trials, fresh replug before each, `usbmon` capturing in parallel both times:

**Trial 1:** didn't reach video `Start` this time (this investigation's already-documented run-to-run variability) — only the first ping (armed immediately after `ServiceDiscoveryResponse`, which always succeeds regardless of this experiment) ever fired. No second attempt was ever gated-and-triggered, because no further reactive frame arrived from the phone before the 120s deadline. Clean timeout, exit code 19. **Confirmed on the phone screen: Error 2.**

**Trial 2:** reached video `Start` cleanly this time (`channel_setup_complete`, `video_render_pipeline_started`, `observing_for_post_start_media_traffic` all printed, no local error) — but the identical thing happened: after the second sensor exchange (`NightMode`), the phone sent nothing further on any channel for the rest of the 120s window. Exit code 0 (`probe_result=observation_window_complete`). Again, only the first ping ever fired; the reactive-triggered gate never got a chance to attempt a second send. **Confirmed on the phone screen: Error 2.**

**This is inconclusive for the question it was built to test** — in neither trial did the experiment ever reach the point of attempting a gated proactive send after the first one, so there's still no direct evidence either way on proactive-vs-reactive versus elapsed-idle-time. But it surfaces a real, new structural fact: **the phone's post-setup silence is not selective to unanswered proactive writes — it stops sending anything at all**, on every channel, a few messages after `Start` (or after the key-binding/sensor exchange, in the run that didn't reach `Start`). This had never been directly established before; every prior trial's narrative was "proactive writes fail, reactive writes keep succeeding indefinitely," which is true as far as it goes, but this pair of trials shows the *reactive* side goes quiet too — there's simply nothing left for the phone to react to once the deterministic handshake sequence this probe implements is exhausted. That reframes "does it recover" and "is it proactive-specific" as two sides of the same underlying fact: the phone isn't distinguishing between message types at this point, it has stopped participating in the session on every axis this probe can observe.

Testing the original question properly would need a different design — something that reliably provokes further genuine reactive traffic from the phone within the failure window (not currently available; this probe's own protocol coverage is already exhausted by that point), or an entirely different diagnostic angle. The opt-in flag is kept in the code as a permanent tool regardless, alongside the survival experiment it builds on.

## LIVI known-good capture (real hardware — decisive: the same phone works end-to-end via LIVI; missing H.265/HEVC codec advertisement is now the leading untested hypothesis)

Following up on suggested next step 5 ("capture a known-good session"), which this document had previously flagged as blocked on separate hardware — it turned out not to be. `f-io/LIVI` (already a formally adopted GPL-3.0-or-later source, `docs/protocol/livi-adoption.md`) ships prebuilt ARM64 Linux AppImage releases and runs directly on this project's own Pi 5, inside the same already-running desktop Wayland session, with no build toolchain needed. The official `LIVI-8.1.0-linux-arm64.AppImage` release asset was downloaded unmodified (never vendored into this repository) and run once, directly, with `DEBUG=1 LIVI_GST_DEBUG=1` and a parallel `usbmon` capture — the same real phone, same cable, same USB port this project's own probe has always used. (Process note: the exact commit SHA pinned in `livi-adoption.md` no longer resolves in LIVI's upstream history as of this trial, likely an upstream rebase/squash since that pin was recorded — but the release version matches, `v8.1.0`, so this is very likely the same functional code; worth re-pinning the adoption record's SHA next time LIVI's source is touched for actual Rust reuse, not just this observational run.)

**The result: a full, real, working Android Auto session, end to end, confirmed on both physical screens** — the head unit (LIVI's own window) showed live projected Android Auto video and UI; the phone showed nothing unusual, which the project owner confirmed is the expected/normal behavior once a session is actually running (matching real-car experience) — not Error 2, not any error screen. This is the single most decisive positive result in this entire investigation: the same phone, same physical setup, that has shown Error 2 in every one of this project's own real-hardware trials works completely normally against a different, more complete implementation.

Confirmed at the raw USB level, independent of LIVI's own logs: the parallel `usbmon` capture recorded **4,664 bulk-OUT writes over the trial's duration, every single one completing with status `0` (success) — zero timeouts, zero `-2`/ENOENT cancellations, zero STALLs.** This is a categorical contrast with every trial this project's own probe has ever run, and it directly answers the open question from "Reactive-triggered proactive-send experiment" above: the phone's endpoint going silent is not an inherent property of this phone, this cable, or this USB stack — it is specific to something this project's own session does (or fails to do) that LIVI's does not. Whatever that gap is, it isn't a hardware or transport-layer limitation.

**The most concrete, well-evidenced candidate for that gap:** LIVI's session log shows `[Session] advertising codecs: h264, h265` in its `ServiceDiscoveryResponse`, and — critically — `[Session] ★ phone picked video codec: H265 (offered: h264, h265)` for *both* the main and cluster video streams. This project's own `ServiceDiscoveryResponse` has only ever advertised `MEDIA_CODEC_VIDEO_H264_BP` — H.265/HEVC has never been offered at all. The phone didn't merely tolerate H.265 when offered alongside H.264 — it actively chose it. Immediately after codec selection, LIVI's log shows sustained real traffic: an 88,458-byte message (almost certainly a real encoded video/audio payload — no message this project has ever observed exceeds roughly 40 bytes) followed by continuous successful exchanges roughly once per second for the entire remainder of the trial, with no failures.

**This is a strong, well-motivated new hypothesis, not yet a proven fix.** It hasn't been tested in isolation — this project hasn't yet added H.265 advertisement itself and re-run against the same phone, so it's not yet known whether codec advertisement alone is sufficient, or whether some other difference in LIVI's greater overall completeness (channel numbering, message content, session bring-up order) also matters. But it is the most concrete, specific, actionable lead this investigation has produced: a phone negotiating an undocumented protocol tier (`1.7`) that visibly prefers a codec this project has never offered, on a session that otherwise reaches every wire-protocol milestone this project's own probe reaches (channel opens, `Setup`/`Config`, key binding, sensors) before going quiet at exactly the point real media would need to start flowing.

This also substantially reframes "the phone stops participating in the session at all" (the leading open question from the two experiments immediately above) — it's very plausibly not the phone deciding to disengage for reasons intrinsic to this session, but the phone waiting for something (real streamable video, in a codec it's willing to accept) that this project's own implementation has never been capable of providing, H.264-only or otherwise. See "Suggested next steps" below — this is now the top priority.

## H.265 advertisement implemented and tested (real hardware, two trials — phone still picked H.264; resolution tier is the next candidate variable)

Implemented the minimal first step from "Suggested next steps" above: `ServiceDiscoveryResponse.MediaSinkService.video_configs` now advertises two entries instead of one — H.264 (position 0) and H.265 (position 1), both at the same existing 800x480@30 tier — and `video_setup.rs`'s `Setup`/`Config`/`Start` handling accepts either codec, tracking exactly which configuration index it offered back so `Start` can only reference the specific index actually negotiated for that session (`crates/protocol-aap/src/service_discovery_response.rs`'s new `VideoCodecType`, `crates/protocol-aap/src/video_setup.rs`'s `ADVERTISED_H264_CONFIGURATION_INDEX`/`ADVERTISED_H265_CONFIGURATION_INDEX`). If the phone ever selects H.265, the probe logs it clearly but does not start the render pipeline — it only has an H.264-typed `GStreamer` pipeline so far, and starting it against H.265 bytes would be a caps mismatch, not a real sink (`auth_discovery_probe.rs`'s `handle_video_start_received`).

Two real-hardware trials, fresh replug before each:

```
...(full handshake through video Start, channel_setup_complete, video_render_pipeline_started — identical to every recent trial)...
probe_state=video_channel_start_received
video_channel_session_id=0
video_channel_configuration_index=0
probe_state=video_render_pipeline_started
probe_state=channel_setup_complete
probe_state=observing_for_post_start_media_traffic
probe_state=ping_request_send_attempt
usb_write_start write_id=26 bytes=42 channel_id=Some(0) timeout_ms=10000
usb_write_error write_id=26 offset=0 elapsed_ms=10000 error=Operation timed out
error=transport I/O: USB error: USB transfer timed out
```

Both trials: `video_channel_configuration_index=0` — **the phone picked H.264, not H.265, despite both being offered** — and both hit the identical write-timeout failure on the very first scheduled proactive ping, exactly the pre-existing baseline behavior. `usbmon` confirmed the same signature both times (25 successful bulk-OUT writes, then one `-2`/ENOENT). **Confirmed on the phone screen: Error 2, both trials.**

This is a real negative result for the narrowest form of the hypothesis (advertising H.265 alone, at the existing 800x480 tier, is not sufficient to make the phone choose it) — but it also surfaces the next concrete variable: re-checking the LIVI known-good capture's log shows LIVI advertised its video configuration at **1280×720**, not 800×480 — `[AaSession] display 1280×720 (AR 1.778) → AA tier 1280×720`. This project has only ever advertised the smaller 800×480 tier, for either codec, in every trial including these two. It's plausible the phone's codec preference (or its willingness to stream at all) depends on resolution tier, not codec availability alone — a phone might reasonably not bother with HEVC's extra decode complexity at a small 800×480 tier, matching what both trials here actually observed (H.264 chosen at 800×480 in both cases), while preferring it at a real "modern" tier like 1280×720 (which is also what LIVI's advertised `codec_resolution` value implies applies to whichever codec the phone selects, not H.265 specifically). Not yet tested: advertising 1280×720 (with either or both codecs) and observing whether that alone changes codec selection, or `Data` delivery, or Error 2 itself. Kept in the code regardless — a real, tested protocol capability with two passing new unit tests (`accepts_h265_setup_and_offers_the_h265_configuration_index`, `rejects_start_at_the_other_codecs_configuration_index`), independently correct whether or not it turns out to be load-bearing for Error 2, matching this document's established disposition for every previously-tested-but-inconclusive increment.

## Original symptom (earlier in this investigation, now superseded)

Before the full-service-catalogue change, the probe reached only as far as:

```
probe_result=service_discovery_summary_received
probe_state=service_discovery_response_sent
probe_tls_state=SSL negotiation finished successfully
error=protocol probe: auth/service-discovery/channel-setup probe timed out before completion
```

with Error 2 on screen immediately after `ServiceDiscoveryResponse` was sent, and no `ChannelOpenRequest` ever arriving. The three hypotheses below were tested against *this* earlier boundary.

## Confirmed facts (from our own real-phone runs, not speculation)

- The phone negotiates and accepts **protocol version 1.7** (`HandshakeStateMachine::negotiated_version()`, surfaced via `probe_negotiated_version=<major>.<minor>` in `auth_discovery_probe.rs`). Version negotiation itself succeeds regardless of what we offer (tested offering both `1.6` and `1.7` — see below).
- **No publicly known AASDK fork documents or implements protocol 1.7.** Checked directly (`Version.hpp`'s `AASDK_MAJOR`/`AASDK_MINOR` constants): our pinned `opencardev/aasdk` @ `9bf6adf933665dee26532201719fac14a047ccf1` (`1.6`); `opencardev/aasdk`'s own `newdev` branch HEAD as of this investigation, pushed as recently as 2026-06-11 (still `1.6` — the most recently active fork checked, and it hasn't caught up either); `openDsh/aasdk` `develop` (`1.1`); `f1xpl/aasdk` (no `Version.hpp` found at the checked path); `n8ohu/aasdk`, `Spooky998/aasdk`, `arash-rasouli/aasdk` (all stale since 2018–2023, not independently re-checked for this constant beyond confirming they're inactive). This looks like a genuine, currently-undocumented-in-open-source gap between what current real Android Auto expects and what any community reverse-engineering effort has reached.

## Hypotheses tested against real hardware and refuted

Each was a deliberately minimal, independently reversible change, verified with the full `cargo fmt`/`check`/`clippy`/`test` sweep before each real-phone run. The first three still ship in the current code (see "What's still in place" below) since each represents a more complete, independently-defensible `ServiceDiscoveryResponse` regardless of whether it fixed Error 2; the version-number and probe-timeout experiments were both reverted since neither changed anything and there was no independent reason to keep them.

1. **Missing audio service.** Added a `ServiceKind::MediaAudio` channel (`protocol_aap::service_discovery_response::AudioCapability`/`AudioStreamType`, `MediaSinkService.audio_type`/`audio_configs`) alongside the existing video/touch channels. **No change in outcome.**
2. **Stale protocol version number.** Temporarily changed `AASDK_PROTOCOL_VERSION` from the pinned source's `1.6` to `1.7` (matching what the phone reports it wants), to test whether a bare version-number mismatch was the trigger. **No change in outcome** — reverted back to `1.6` (the pinned, documented value) once refuted, since Android Auto's version negotiation is designed to be backward-compatible and a real phone accepting-but-rejecting on version number alone was never a well-motivated theory to begin with; the experiment confirmed that reasoning rather than contradicting it.
3. **Missing head-unit identity.** Populated `ServiceDiscoveryResponse.headunit_info` (field 17, `HeadUnitInfo` — `protocol_aap::service_discovery_response::HeadUnitInfo`) with fixed, non-sensitive project-identifying strings (project name, `CARGO_PKG_VERSION`, etc. — never real vehicle/user data). Theory: Android Auto's app-level validation might reject a head unit that never identifies itself, distinct from the wire schema (which marks every `HeadUnitInfo` field `optional`). **No change in outcome.**
4. **Probe timeout too short.** Once every currently-implemented handshake step started succeeding (after the `SpeechAudio` increment), the probe began timing out instead of being rejected on a new message. Temporarily raised `PROBE_TIMEOUT` (`auth_discovery_probe.rs`) from 10s to 30s, to test whether the phone just needed more time before sending whatever comes next. **No change in outcome** — the same handshake steps completed and it still timed out waiting for more, just with three times as long to wait. Reverted back to 10s once refuted.
5. **Missing sensor-capability advertisement.** `ServiceDiscoveryResponse.Sensors` had never advertised any supported `SensorType`, so a real phone had no way to know it could request `DRIVING_STATUS`/`NIGHT_DATA` — described in research as eager/near-mandatory session-bring-up behavior in `OpenAuto`'s reference implementation (see "Systematic `OpenAuto` diff" above). Implemented `SensorCapability`/`sensor.rs`/`SensorsChannel`, advertising and handling both types. **No change in outcome** on the first (neutralized-ping) trial — the phone opened the Sensors channel but never sent a `SensorRequest`. A later trial (with ping active, then again with ping neutralized — see item 6 below and the `NavFocusRequest`/`ByeByeRequest` section above) *did* observe the phone sending `SensorRequest` for both types, correctly answered — still **no change in Error 2 outcome**. Kept in the code (a more complete, independently-correct `ServiceDiscoveryResponse` regardless).
6. **Missing `NavFocusRequest`/`ByeByeRequest` handling.** Two more control-channel gaps named by the same systematic `OpenAuto` diff. Implemented `nav_focus.rs`/`byebye.rs`, answering `NavFocusRequest` with a hardcoded `Projected` and `ByeByeRequest` with an empty response (treating receipt as a clean probe stop, not an error). **No change in outcome** — neither message ever arrived across two real-phone runs (one with the write-timeout confound, one clean), even after the phone completed the full sensor exchange for the first time. Kept in the code regardless.
7. **Ping write-timeout: plain vs. encrypted framing.** Switched `PingRequest` from `Encryption::Plain` (matching AASDK's own `sendPingRequest`) to TLS-encrypted, on the theory a real `1.7` client might desync on a stray plain frame mid-session. **No change in outcome** — the write still timed out, confirmed (via a bracketing diagnostic print) to still be the ping write itself. Left encrypted (independently reasonable, matches every other post-handshake message) even though it didn't fix the timeout.
8. **Ping write-timeout: transport timeout too short.** Raised `crates/transport-usb/src/linux.rs`'s bulk-OUT write timeout from 2s to 10s, matching AASDK's own reference value (`USBTransport.hpp`'s `cSendTimeoutMs = 10000`) exactly. **No change in outcome** — the write still timed out even given 5x more time, ruling out "the phone was just briefly slow." Left at 10s (matches the reference implementation regardless).
9. **Missing unsolicited `VideoFocusNotification` after video `Config`.** Found via direct comparison against a second, independent, working Android Auto implementation (`f-io/LIVI`) rather than the AASDK/`OpenAuto` sources everything else in this document is sourced from. Implemented `video_setup.rs`'s `encode_video_focus_notification`, sent as a second action right after `Config`. **This is not "no change in outcome" like every item above** — the phone sent `Start` on the video channel for the first time in this entire investigation, and the probe reached its own internal success condition. Error 2 still appeared on the phone screen regardless — see the `VideoFocusNotification` section above for why that's now understood differently (likely missing real media data, not a further handshake gap). Kept in the code — this is the most load-bearing single change in this document's history.
10. **Missing `MEDIA_MESSAGE_ACK`.** Found via a comprehensive, whole-session `f-io/LIVI` audit — this project advertised `Config.max_unacked = 1` on every AV channel but never sent an `Ack`, so the phone could send at most one unacknowledged frame. Implemented `encode_media_ack`/`decode_media_data` (shared, `media_message.rs`), wired into every AV channel's `Open` state. Kept in the code (independently correct regardless of the outcome below).
11. **Over-strict `KeyBindingResponse`.** Same audit — LIVI answers unconditionally `Success`; this project validated against its own (empty) advertised keycode list. Fixed. No real request has ever been non-empty, so this has not yet been observed to change anything, but it's a confirmed correction.
12. **Observation window too short to see `Data`.** After (10)/(11), a real-hardware run reached `Start`, ran its full observation window, and completed with no local error at all — but only ~1-2 real seconds elapsed post-`Start` before the (then-10s) `PROBE_TIMEOUT` fired. Raising `PROBE_TIMEOUT` to 30s (a minimal, reversible change directly analogous to the earlier 10s→30s handshake-timeout experiment) and re-running produced the same clean completion, this time with the full 30-second window elapsing — still no `Data`/`CodecConfig` ever arrived. **Refuted**: whatever is stopping the phone from streaming, it isn't a head unit that gives up too soon. See "30-second observation window" above.
13. **AOA accessory identity strings.** Swapped `usb_auth_discovery_probe`'s `AoaIdentification` preset from this project's own `uri`/`serial` (`receiver_probe()`) to the exact pinned-AASDK reference values (`aasdk_compatibility_probe()`), combined with the real operator-authorized TLS credential — a combination never tried before (the one prior use of the reference identity was with a now-permanently-disabled temporary generated credential, rejected with the unrelated error 7). Two real-hardware trials, both Error 2; neither reached `Start`, but this investigation's own documented run-to-run variability makes that inconclusive as evidence of a regression. **No evidence this identity helps.** Reverted to `receiver_probe()`. See "AOA identity experiment" above.

14. **Missing `connection_configuration.ping_configuration` advertisement.** LIVI advertises a 1500ms ping cadence in `ServiceDiscoveryResponse`; this project never populated the field. Implemented (interval only, no fabricated values for the other three sub-fields). One real-hardware trial: still Error 2, but the run didn't reach video `Start` this time, so — consistent with this investigation's own documented run-to-run variability — the trial is **inconclusive, not refuted**. See "Ping cadence advertisement experiment" above.
15. **Wrong ping arm-timing/cadence as the write timeout's root cause.** LIVI (now formally adopted, `docs/protocol/livi-adoption.md`) arms its ping timer immediately after `ServiceDiscoveryResponse` at 1500ms, not before `VersionRequest` at 5000ms like the `OpenAuto`-derived model every prior ping trial used, plus a 5000ms local watchdog. Implemented exactly (`PingState`, `PING_INTERVAL`, `PING_WATCHDOG_TIMEOUT`). **Partially refuted:** the first, correctly-timed `PingRequest` got a real `PingResponse` for the first time ever — but the second scheduled ping still hit the identical write timeout. Wrong timing is not, by itself, sufficient to explain the write timeout. See "LIVI formally adopted; real ping-timing trial" above.
16. **Missing `VideoConfiguration.ui_config` advertisement.** LIVI populates `margins`/`content_insets`/`stable_content_insets` on every video config; this project never populated the field (it's been "not yet mapped" in `docs/protocol/aasdk-adoption.md` since this project's earliest protocol work). Implemented with LIVI's own default (all-zero insets, applicable directly since this project has no display-specific customization). **No change in outcome** — real-hardware-tested (nineteenth run): reached `Start`/`channel_setup_complete` again, same as the immediately preceding trial, still Error 2. See "`ui_config` implemented; USB writes instrumented" above.
17. **Second-write failure is specific to `PingRequest`'s content/message type.** Tested directly via the `AA_HEADUNIT_PING_ISOLATION` experiment: substituted a harmless non-ping message (a duplicate `VideoFocusNotification`) for the second scheduled proactive send instead of a second `PingRequest`. **Refuted, decisively** — the substituted message hit the identical `write_bulk`-blocks-for-10s failure, at the same point in the session. The failure is about *a second proactive/unsolicited write of any kind* at this point, not about `Ping` specifically. Local causes (clock desync via `timedatectl`, USB power/signal via `vcgencmd get_throttled`) were also checked and ruled out. See "Ping isolation experiment" above.
18. **The write timeout is a USB STALL / explicit device-side protocol rejection.** Tested directly with a raw `usbmon` capture of a full real-hardware run. **Refuted** — every failing write is submitted normally and identically to every succeeding one, then sits pending until this project's own 10s timeout cancels it (`usbmon` status `-2`/`ENOENT`, the same code its own routine read timeouts show); no transfer in the trace ever completes with a `STALL`/`EPIPE`-class status. The phone's endpoint never explicitly rejects anything — it just never answers the failing write. See "`usbmon` capture" above.
19. **The write-timeout endpoint is only temporarily busy and recovers on its own.** Tested by making a proactive-write timeout non-fatal (instead of ending the whole probe) and extending the observation window to 120s, so the session could survive long enough to attempt several more proactive sends after the first failure. **Refuted, decisively** — 11 consecutive scheduled proactive sends in a row (attempts 2 through 12) all failed identically over the following ~110 seconds; not one recovered. Confirmed at the raw USB level (`usbmon`: 25 successful writes, then 11 consecutive `-2`/ENOENT completions, no STALL). See "Proactive-write survival experiment" above.
20. **A proactive send closely coupled to genuine reactive traffic succeeds where a bare-timer one fails.** Tested by gating every proactive send on immediately following a real, decoded, dispatched message from the phone, across two real-hardware trials. **Inconclusive, not refuted or confirmed** — in both trials, the phone stopped sending anything at all (reactive or otherwise) a few messages after `Start`, so the gate never got a chance to trigger a second attempt in either run. This does establish something new, though: the phone's post-setup silence isn't selective to proactive writes, it's total. See "Reactive-triggered proactive-send experiment" above.

The fifth hypothesis (proactive `PingRequest`, "Ping/liveness experiment" above) remains **inconclusive, not refuted** — the probe crashed locally (a USB bulk-OUT write timeout) before it could be fairly tested in its own right, and two direct attempts to fix that write timeout (items 7 and 8 above) both failed to resolve it. That local failure needed to be worked around (temporarily neutralizing `PING_INTERVAL`) to test the Sensors, `NavFocusRequest`/`ByeByeRequest`, and `VideoFocusNotification` hypotheses cleanly (the `VideoFocusNotification` breakthrough run above notably had `PingRequest` active and completed without hitting the write timeout at all, since the session ended — via `Start`'s success condition — before the 5s ping interval fired). The write timeout's root *cause* is still unresolved; it now looks most consistent with the phone itself having already stopped servicing the USB connection at that point in earlier runs, for reasons unrelated to ping's own content or timing.

## What this rules out, and what it doesn't

Ruled out: a simple missing-channel gap; a simple version-number-field mismatch; a simple missing-identity gap; a too-short probe timeout (30s produced no change over 10s at the handshake level, and separately, a 30s post-`Start` observation window produced no `Data` either — the phone appears to genuinely stop sending anything relevant once it decides to fail, not just pause); a missing sensor-capability advertisement; missing `NavFocusRequest`/`ByeByeRequest` handling; the ping write-timeout being caused by plain-vs-encrypted framing or too-short a transport timeout; a missing `MEDIA_MESSAGE_ACK`/over-strict `KeyBindingResponse` being what's blocking media data (both fixed, no change in outcome); a too-short post-`Start` observation window (30s produced the same result as ~1-2s); the AOA accessory identity strings (this project's own `uri`/`serial` vs. the exact pinned-AASDK reference values — swapping showed no evidence of helping across two trials); a bare protocol-version-number claim as sufficient by itself (confirmed twice, independently — this project's own `1.6`-vs-`1.7` experiment showed no difference, and LIVI's own history shows they backed their `1.7` claim with real new message support rather than claiming it for free, see "Does LIVI avoid Error 2 by tracking a fresher protocol?"); wrong ping arm-timing/cadence as the sole cause of the USB write timeout (LIVI's exact timing got a real first `PingResponse` but still hit the identical timeout on the second ping — see "LIVI formally adopted; real ping-timing trial"); `PingRequest`'s content/message-type being the write timeout's cause (a substituted non-ping message hit the identical failure — see "Ping isolation experiment"); `ui_config` as an Error-2 fix (real-hardware-tested, no change); local clock desync or USB power/signal issues as an explanation for the write timeout (`timedatectl`/`vcgencmd get_throttled` both clean); a USB STALL or any other explicit device-side protocol rejection as the write timeout's mechanism (`usbmon` capture: the failing write is submitted identically to every succeeding one and simply never answered, cancelled only by this project's own 10s timeout — see "`usbmon` capture"); the write-timeout endpoint being only temporarily busy and recovering on its own (11 consecutive proactive-write attempts across ~110 seconds all failed identically, zero recoveries — see "Proactive-write survival experiment"); and, most significantly, **a missing wire-protocol handshake step through `Start`** — every step through video `Start` (the deepest point Android Auto's wire protocol requires before real media begins) is now real-hardware-confirmed correct, including the previously-undiscovered unsolicited `VideoFocusNotification`.

**Not ruled out**, in roughly descending order of how well-motivated they are:

- **Missing 1280×720 (or larger) resolution tier.** Refined from the H.265 hypothesis below after two real-hardware trials: this project has only ever advertised the 800×480 tier, for either codec; LIVI advertised 1280×720. Now the leading specific, testable candidate — see "H.265 advertisement implemented and tested" above.
- **Missing H.265/HEVC codec advertisement, alone.** The leading hypothesis from the "LIVI known-good capture" above, now tested in isolation and found insufficient on its own: H.265 advertisement was implemented (schema-only, same 800×480 tier) and real-hardware-tested twice — the phone picked H.264 both times, not H.265. Not fully refuted as a contributing factor (it's still advertised, still available, and may matter in combination with a larger resolution tier — LIVI advertised both together, never separately), but advertising it alone, at the existing tier, does not change the phone's behavior. See "H.265 advertisement implemented and tested" above.
- **The phone never intends to send real media data on this session at all** — the leading theory before the LIVI capture above, and still plausible as a *contributing* factor even if codec advertisement turns out to be the primary gap: this project has never sent a single byte of actual video/audio stream data (separate M3 encode/render pipeline work, now built but never fed real phone data — see "Real GStreamer decode/render pipeline"). With the window-length and flow-control (ack) explanations both ruled out, a real phone plausibly needs to see the head unit *also* behaving like a real sink before it will commit to streaming. Testing this now depends on first closing the codec gap above, since a phone that never selects a codec this project supports has no path to ever test whether the render pipeline itself is sufficient.
- **A genuine 1.7 schema change** elsewhere in the protocol that this project has no source for. Weakened as a leading theory now that `Start` has been reached correctly and the ack/keybinding gaps are closed, and further weakened by the LIVI research below (a bare `1.7` claim, independently confirmed on both sides to not be self-sufficient) — but not eliminated for whatever comes after `Data` starts flowing (if it ever does), since LIVI's own `1.7` capability additions (nav) are not the only ones that could exist and haven't all been audited.
- **A framing/encryption detail specific to a real phone's TLS stack** that the project's own real-TLS integration tests (`encrypted_service_discovery.rs`, `full_channel_setup.rs`) can't catch, since those exercise the same Rust encrypt/decrypt code on both sides of a controlled fake-phone harness rather than a genuinely independent TLS implementation.
- **The USB write timeout happens on *some* proactive, unsolicited write in the session — not to `PingRequest` or its content, and the phone never explicitly rejects it.** Now the leading theory for the write timeout specifically (distinct from the leading theory for Error 2 itself, above): every reactive write (a response to something the phone just sent) succeeds indefinitely throughout the session; only a head-unit-initiated write eventually fails, and it fails identically regardless of what it contains (confirmed with a genuinely different message type, "Ping isolation experiment") and without any device-reported protocol error (confirmed at the raw USB level, "`usbmon` capture" — no `STALL`, the write just goes unanswered until this project's own timeout gives up). *Which* proactive send fails isn't a fixed count — the second in most trials, the third in the `usbmon` trial — consistent with this investigation's documented run-to-run variability in session progression. Once it starts failing, it stays failing: the proactive-write survival experiment observed 11 consecutive attempts across ~110 seconds, none recovering, ruling out a transient/temporarily-busy explanation on that timescale (see "Proactive-write survival experiment"). A follow-up pair of trials gating proactive sends on genuine reactive traffic found the phone's silence isn't actually selective to proactive writes at all — it stops sending anything, reactive or otherwise, on any channel, a few messages after `Start` (see "Reactive-triggered proactive-send experiment") — so "proactive vs. reactive" may be the wrong axis entirely; "has the phone stopped participating in this session at all past a certain point" fits the evidence at least as well. Not yet explained *why* the phone's endpoint stops answering proactive writes (or sending anything else) at some point — but the LIVI known-good capture above now proves it isn't inherent to the phone, cable, or USB stack: the identical phone on the identical hardware exchanged 4,664/4,664 successful bulk-OUT writes with LIVI in one trial, with no failures at all. The best-supported reading is now that the phone's own Android-Auto stack stops actively servicing the connection specifically because this project's session never gives it a reason to keep going (most plausibly the missing H.265 codec offer, above) — not a property of the connection itself.
- Something else entirely not yet considered.

**New observation, not yet well-motivated as a hypothesis:** the three most recent real-phone runs (all after every currently-implemented handshake step succeeds) did *not* reproduce the same message sequence — Run 1's phone stopped sending anything right after the key-binding exchange (no audio `Setup` ever arrived), while Runs 2 and 3 sent all three audio channels' `Setup` and video's `Config` before going quiet. All three ended in Error 2 regardless, and Run 3 confirms the phone isn't simply pausing before continuing (30s produced the same outcome as 10s). This run-to-run variability could mean Android Auto itself is retrying/backing off internally before declaring incompatibility (rather than following one fixed message sequence), or it could be ordinary session jitter unrelated to the eventual failure. Not enough data yet to tell which.

## Suggested next steps for whoever picks this up

1. **Top priority: advertise a larger resolution tier (1280×720) and re-test.** H.265 advertisement alone (implemented, real-hardware-tested twice) did not change the phone's codec choice — it picked H.264 both times, at this project's existing 800×480 tier. The LIVI known-good capture advertised its video configuration at 1280×720, not 800×480 — a real, concrete difference beyond codec availability that this project has never tested. Minimal next step: add (or switch to) a `VideoCodecResolution::Video1280x720` capability entry, for H.264, H.265, or both, and observe whether that alone changes codec selection, `Data` delivery, or Error 2. See "H.265 advertisement implemented and tested" above.
2. **If resolution tier alone doesn't resolve it either:** find out what else LIVI's session does differently. The known-good capture's log is a byte-level reference for channel numbering, message ordering, and content that a future pass could diff against this project's own implementation more systematically, the same way the original `VideoFocusNotification`/ack/`KeyBindingResponse` gaps were found via LIVI comparison earlier in this document — except this time against a *working* session log instead of source code alone.
3. **Does the phone actually sending `Data` change anything, now that there's a real sink to receive it?** The real decode/render pipeline is now built and proven against real hardware (`probe_state=video_render_pipeline_started`, no error) — see "Real GStreamer decode/render pipeline" above. It currently only handles H.264; the phone has never once selected a codec/resolution combination that gets it streaming, so this remains untestable until item 1 (or item 2) changes that.
4. **Done, refuted/no-change:** `ui_config` + USB write instrumentation, the ping-isolation experiment, a raw `usbmon` capture, the proactive-write survival experiment, the reactive-triggered proactive-send experiment, and H.265 codec advertisement (at the existing 800x480 tier) were all run on real hardware. `ui_config` shows no evidence of helping; H.265 alone didn't change codec selection. The write-timeout question is now resolved at the "what" (a proactive/unsolicited write of any kind, not `PingRequest` specifically), "how" (the phone's endpoint never explicitly rejects it — no STALL — it just never answers, and this project's own 10s timeout eventually cancels the transfer), "does it recover" (no — 11 consecutive attempts across ~110s all failed identically), and "is it inherent to the phone/hardware" (no — proven false by the LIVI capture's 4,664/4,664 successful writes) levels. See "Ping isolation experiment", "`usbmon` capture", "Proactive-write survival experiment", "Reactive-triggered proactive-send experiment", "LIVI known-good capture", and "H.265 advertisement implemented and tested" above.
5. LIVI's remaining candidate scope (`docs/protocol/livi-adoption.md`) not yet pursued: `driver_position`, `display_name`, `probe_for_support` (all low-confidence, cheap completeness additions), and a full field-by-field trace of `InputChannel.ts`/`MicChannel.ts`/`NavigationChannel.ts` (not completed this pass — see "`ui_config` implemented; USB writes instrumented" above).
6. Given the run-to-run variability observed across this investigation (see "What this rules out, and what it doesn't"), don't over-index on a single run's exact message sequence — repeat any experiment at least twice before drawing conclusions, as this session did for the `SpeechAudio`, Ping, Sensors, `NavFocusRequest`/`ByeByeRequest`, observation-window, and AOA-identity real-hardware tests.
7. Re-check whether any AASDK fork has been updated since this investigation (2026-08-14) — the ecosystem may catch up.
8. If continuing to experiment against real hardware, keep changes as minimal and independently reversible as every increment so far, and keep running the full verification sweep before each real-phone cycle.
