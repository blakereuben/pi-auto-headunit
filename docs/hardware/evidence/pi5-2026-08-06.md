# Pi 5 evidence - 6 August 2026

## Credential-aware ARM64 package

The Pi 5 reference system built and installed the credential-aware Debian package natively from the repository content through commit `de5e535`.

- Target: Raspberry Pi 5 Model B Rev 1.0
- OS: Debian GNU/Linux 13 (Trixie), `aarch64`
- Kernel: `6.18.39+rpt-rpi-2712`
- Package: `/home/blakereuben/aa-headunit-diagnostics_0.1.0-1_arm64.deb`
- Package size: 302,964 bytes
- SHA-256: `d62172ee819a188a4f875746133b33ea25b456e09b732a447883ea229ed69c5c`
- Workspace tests during package build: 75 passed, 0 failed

The first build attempt exposed Windows line endings in Debian metadata and a missing executable mode on `debian/rules`. Commit `dd394ec` adds an LF repository policy and records the executable mode. Package inspection then showed that `dh_fixperms` changed the credential directory to `0755`; commit `04a3f62` adds an explicit final `0700` correction.

Final package inspection verified:

- `/etc/aa-headunit/credentials/` is present, empty, owned by `root:root`, and mode `0700`;
- the package contains no `.pem`, `.key`, `.crt`, `.p12`, or `.pfx` files;
- a byte scan of every extracted package file found no certificate or private-key PEM marker;
- the default configuration points to `/etc/aa-headunit/credentials/headunit.crt` and `/etc/aa-headunit/credentials/headunit.key`;
- no credential contents were logged.

## Installed credential-state checks

All checks were offline and opened no phone, USB, or network transport.

- Missing configured files: rejected with a clear `credentials are not configured` result.
- Deliberately mismatched synthetic certificate/key pair: rejected.
- Matching one-day synthetic certificate/key pair with private-key mode `0600`: accepted.
- Installation into the default protected directory: accepted.
- Status through `/etc/aa-headunit/config.toml`: accepted.
- Second installation attempt: rejected without overwriting the installed pair.

The installed synthetic files and their dedicated temporary test directory were deleted after verification. They were disposable and are not recoverable. The production credential directory was rechecked and is empty. No user-supplied or third-party credential was transferred to or read on the Pi.
