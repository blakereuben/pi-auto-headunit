# Milestone Checklist

This is the operational progress tracker for the project. Detailed requirements and exit criteria remain in `PRD.md`, `ARCHITECTURE.md`, and `MILESTONES.md`.

## Execution rule

**No physical Pi 4, CM4, or CM5 compatibility testing begins until the Pi 5 reference system has complete wired Android Auto, complete wireless Android Auto, appliance startup, packaging, and stability evidence.**

Architecture and automated tests must remain portable throughout development, but the Pi 5 is the only physical implementation target until the Pi 5 completion gate is checked.

  **Real bugs found and fixed while building this (all real-hardware-confirmed 2026-08-16)**, recorded here since they were found in the course of touch/rotation work even though most aren't rotation-specific: (1) the arming swipe's distance check originally measured "moved down" in already-rotation-adjusted target-space coordinates, so a real physical downward swipe stopped registering the instant the operator changed rotation, since a rotated remap no longer produced an increasing target Y at all — fixed by measuring straight-line displacement magnitude instead, which every one of the four rotations preserves (`crates/platform-api/src/gesture.rs`). (2) `usb gtk-dev-ui`'s hang-safety-net timer was a fixed 120-second constant unaware of `AA_HEADUNIT_OBSERVATION_WINDOW_SECONDS`, so a deliberately longer test window was silently cut off mid-session, killing the whole window/process — fixed by deriving the safety net from the same override plus a margin (`gtk_dev_ui.rs`). (3) the original "return to desktop" action only ever left fullscreen, with no gesture-driven way back — fixed by making it a real bidirectional toggle (`Action::ToggleFullscreen`, `gesture_settings.rs`), and the settings panel gained a plain "Close" button that doesn't touch window state at all (closing the panel and un-fullscreening had been incorrectly tied together). (4) a three-finger tap's own naturally-staggered real-hardware landing/lifting (fingers never touch or release in perfect lockstep) let its lone leading single-finger frame contaminate the independent double-tap recognizer's state, so an unrelated later tap could complete a spurious `DoubleTap` — fixed by tracking each touch episode's peak simultaneous finger count and gating/resetting the single-finger recognizers the moment an episode reveals itself as multi-finger (`crates/platform-api/src/gesture.rs`). (5) the three-finger tap's own release detection required catching an exact "still 3 fingers, now lifting" frame, which `MultiTouchTracker`'s documented one-transition-per-frame behavior often skips entirely on real releases — fixed by firing as soon as the count drops below three, not waiting for that exact frame.

  **App-category switching via swipe gestures, real-hardware-confirmed 2026-08-16.** At the operator's request, the three-finger tap became a two-finger tap (`GestureId::TwoFingerTap`, `TWO_FINGER_COUNT`, since three fingers weren't needed for anything else), and four new single-finger follow-up gestures — `GestureId::SwipeUp`/`SwipeDown`/`SwipeLeft`/`SwipeRight` — were added, defaulting to `Action::SwitchToNavigation`/`SwitchToMedia`/`SwitchToPhone`/`SwitchToRadio` respectively (fully reassignable, `gesture_settings.rs`). Every single-finger outcome (tap, long-press, or one of the four swipe directions) is now classified by one unified `SingleFingerGestureRecognizer` (`crates/platform-api/src/gesture.rs`) rather than independent recognizers racing each other, deliberately avoiding the exact bug class fixed in (4)/(5) above.
